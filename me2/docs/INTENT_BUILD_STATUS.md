# `set_alarm` — implementation notes (built 2026-09-28)

Status: **built and tested.** 26 timer tests pass; full suite 113/113 green.

## What shipped
- **Self-contained ring** (no OS GUI alarm app). Reuses the `threading.Timer`
  machinery already proven for countdown timers. Works headless.
- **Single-shot, in-process.** Does not persist across a reboot (v1 decision).
- **Roll-forward.** If the requested time is already past today, it fires the
  next day (e.g. "7am" said at 10pm → rings 7am tomorrow).
- **Independent of countdown timers.** An alarm and a timer can both be armed;
  cancelling one never touches the other.

### Expiry sounds (added 2026-09-28)
Before this, both expiry events played the same soft `ack_beep.wav` — indistinguishable
from the wake acknowledgement. Now each has a distinct synthesized tone:

| Event | WAV | Character |
|---|---|---|
| Timer ends | `assets/replies/timer_ding.wav` | gentle rising triple-ding (C6→E6→G6), 0.60 s, light |
| Alarm rings | `assets/replies/alarm_ring.wav` | urgent repeating low buzz ×4, 1.48 s, full |

- Generated by `scripts/make_expiry_sounds.py` (pure stdlib: `math`/`wave`/`struct`,
  22050 Hz mono 16-bit to match the other assets). Re-run it any time to regenerate.
- `run.py` defaults updated: `--timer-expiry-wav` → `timer_ding.wav`,
  `--alarm-expiry-wav` → `alarm_ring.wav`.
- **Path gotcha:** the harness `cd`s to `me2/` (see `run_pi5_harness.sh`), so the live
  assets dir is `me2/assets/replies/` — NOT `rpi5/assets/replies/`. Both new files live
  in `me2/assets/replies/`.

### Lights (added 2026-09-28)
The three light intents are now live via a **pluggable driver layer** in `rgb.py`,
deliberately separate from the demo-lifecycle `RgbController` (which still drives
the ring's listening/processing/speaking colours). The ring can wear both hats at
once; swapping the device behind a voice command never touches the lifecycle
indicator.

- **`LightDriver`** (abstract) — `on()`, `off()`, `set_brightness(pct)`,
  `available()`, `close()`. Stateful: remembers the last brightness so a bare
  "on" restores it.
- **`HyperxDuoCastDriver`** — default target. Drives the HyperX DuoCast mic ring
  via the `quadcastrgb` CLI (`solid <RRGGBB>`). The ring has no separate
  brightness channel, so brightness is expressed by scaling a warm-white colour
  (`FFF4E6`) toward black. Executable resolves from `$QUADCASTRGB` → `PATH` →
  `--light-executable`. If the tool is absent it **degrades to a no-op**
  (`available()==False`) rather than raising, so the assistant answers honestly.
- **Swapping devices:** subclass `LightDriver`, add one line to the
  `LIGHT_DRIVERS` registry, select it with `--light-driver NAME`. No code change
  in the executor or orchestrator. Unknown name → logged + falls back to dry-run.
- **CLI:** `--light-driver` (default `hyperx-duocast`; empty string = dry-run),
  `--light-executable PATH`. Wired through `run.py` → `FacadePipeline` →
  `default_orchestrator(light_driver=...)` → `LightExecutor`.
- **Tests:** `tests/test_lights.py` (registry, colour scaling, degrade-when-absent,
  executor on/off/dim + failures, dry-run fallback, full-stack orchestration).

### HVAC (added 2026-09-28)
`set_temperature` is now **audio-only**: the recognized set-point is validated
and confirmed back by voice. No relay/controller is wired, so nothing physical
is touched — the "side effect" is the spoken confirmation plus a structured
`payload` a future controller can consume without re-parsing speech.

- **Slot:** arrives as `temperature` (see `model/slots.py` and the facade's
  `INTENT_SPECS`). Valid band **10–35 °C**.
- **Validation is layered.** The facade gate already rejects out-of-band /
  missing / non-numeric values as `invalid_slot` *before* the executor runs
  ("Sorry, that didn't work."). The `HvacExecutor` re-checks the same band as a
  defensive backstop, so it is safe even if the gate is bypassed.
- **Reply:** `Setting the temperature to {n} degrees.` — carried in
  `payload["answer"]`, which the orchestrator prefers over the facade template
  when present. `payload` also carries `{"temperature": n, "unit": "C"}`.
- **Future controller:** to make it physical, attach a controller in
  `HvacExecutor._live` (mirror how `LightExecutor` drives its `LightDriver`)
  and flip `side_effects=True`. The slot and payload are already shaped for it.
- **Tests:** `tests/test_hvac.py` (facade gate, executor valid/edges/unsupported/
  defensive-bad-slot, dry-run fallback, full-stack orchestration).

## Design decisions (to confirm)

### A. What does "ring" mean on the Pi5?
The user suggested a **Pi5-native alarm clock app**. Options, in order of fit:

1. **Self-contained (recommended).** Reuse the existing timer-expiry machinery.
   `TimerManager` already has an `on_expire` callback that `run.py` wires to play
   `assets/replies/ack_beep.wav` + TTS "Your timer is up." For an alarm we:
   - compute seconds-until-target-time (roll to next occurrence if already passed),
   - schedule via the same `threading.Timer` path,
   - fire a distinct alarm sound + TTS "It's 7am. Time to wake up."
   No external dependency, works headless, survives the existing lifecycle
   (`timer_manager.close()` at `run.py:492`).

2. **Native GUI app.** Drive a desktop alarm app (e.g. the OS clock) over the
   display server. Heavier: needs a graphical session, fragile to launch, and the
   Pi5 is typically headless. Only worth it if we specifically want the OS alarm UI.

**Decision: go with Option 1 (self-contained)** unless you explicitly want the OS
alarm UI. It's consistent with how `set_timer` already works and keeps the device
headless-friendly.

### B. Alarm semantics
- **Slot:** `time` is a string (e.g. `"7am"`, `"07:00"`, `"19:30"`). Need a parser
  → `(hour, minute)`. Reuse/extend whatever the facade already extracts for `time`.
- **Single-shot vs recurring:** start **single-shot** (one alarm, fires once).
  Recurring/daily alarms can be a follow-up.
- **Already-past times:** if target is earlier than now, roll to **next day**
  (or reject — decide; default: roll forward 24h).
- **Multiple alarms:** `TimerManager` currently tracks a single active timer
  (`_cancel_locked`, single `state`). Decide: keep one active alarm for v1, or
  extend to a list. **Default: one active alarm** to match current manager shape.

### C. Persistence
Countdown timers don't persist across restarts. For an alarm, decide whether it
should survive a reboot (write to a small JSON, like `ReminderStore` does).
**Default for v1: no persistence** (in-memory), matching timer behavior. Add later.
